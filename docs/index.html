Why stages 1 and 2 are free

DDP's all-reduce is a reduce-scatter followed by an all-gather. ZeRO-1 and ZeRO-2 do the same two halves, but in between they stop and use the slice: the reduce-scatter leaves each GPU holding the summed gradient for exactly the slice it owns, it updates that slice, and the all-gather moves the new weights instead of the gradients. Same bytes, same count. ZeRO-3 has no weights to keep, so it gathers them twice, before the forward and before the backward: one more P.

09

Pros, cons, and what I would pick

For V5 (30B)

DDP and ZeRO-1 never fit at any GPU count: bf16 weights + gradients alone are 4 B × 30B = 111.8 GiB per card. That leaves ZeRO-2 on 32+ GPUs (68.1 GiB, tight once activations arrive) or ZeRO-3 on 8+ (55.9 GiB, +50% traffic). My timeline says ZeRO-3's extra P hides behind compute if the next layer is prefetched; my topology test says the inter-node link, not the GPU count, sets the price. So I would start V5 on ZeRO-3 with prefetch, hierarchical collectives, communication logged as a share of compute from step one, and measure the peak, not the steady state.

10

What bit me while building it

every one of these was silent
bug 1 · the ranks were not identical

32 threads, one random generator

Every GPU builds the model from seed 0, which should give identical weights. It did not: torch.manual_seed is process-wide, so 32 threads were seeding and drawing from the same generator at once. Two runs of the same config disagreed at step 0. Fixed with a lock, which is what DDP's broadcast-from-rank-0 guarantees for free.

bug 2 · clipping 32× too hard

The norm of the sum is not the norm of the mean

My shards hold summed gradients; I divide by N only in the update. I computed the clipping norm on the sums, so at N=32 it was 32× too large and clipping fired every step. Loss still went down, so nothing looked wrong. The test "N GPUs = 1 GPU on an N× batch, in fp64" caught it with a 4e-4 gap.

bug 3 · three weights out of 818,241

Bit-identical except the last nine elements

ZeRO-1's fp32 master differed from DDP's in 3 elements by 1e-9. All in the tail of a 1,081-element slice: the CPU's SIMD loop uses fused multiply-add, the scalar tail loop does not. Padding every slice to a multiple of 16 made all four arrangements bit-identical. Real libraries pad shards for similar reasons.

bug 4 · a network faster than physics

Sending before the receiver is listening

My first clock let a GPU push a chunk to its neighbour before the neighbour had entered the collective, so the ring finished 7% faster than (N−1)/N × P / bandwidth allows. NCCL writes into a buffer the receiver posts. Adding that handshake put DDP's network share on the lesson's 34% × 31/32, within my 0.24% shard padding.

lesson 5 · out of memory, simulating a memory saver

The peak found me before I found it

My notebook died of out-of-memory twice on an 8 GB laptop. First because every run kept 32 GPUs' worth of weights alive for the equality checks. Then because, at the peak of a step, all 32 ranks hold their activations at the same moment, which is exactly the part of memory that §04 shows no ZeRO stage touches. The reported run moved to a 16-core cloud CPU box.

lesson 6 · reading my own debug output

"Exactly zero" that wasn't

For a moment PyTorch's losses and mine looked exactly equal. They weren't: my debug print rounded to four decimals. The real gap is fp32 rounding, a few times 1e-8. Every number on this page is printed from the results file, not from my notes, for that reason.
